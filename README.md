# MultiDrive Pool

Pools multiple personal Google Drive accounts into one virtual store. Files above
a chunk size (default 3GB) get split and spread across whichever accounts have
the most free space; download reassembles transparently. One web UI, no account
juggling.

Uses `drive.file` scope only — the app can only see/touch files it creates
itself in a `MultiDriveStore` folder in each Drive, nothing else in your account.

## 1. Google Cloud OAuth setup (one-time, ~5 min)

1. https://console.cloud.google.com → new project (any name).
2. **APIs & Services → Library** → enable **Google Drive API**.
3. **APIs & Services → OAuth consent screen**:
   - User type: External. App name/support email: anything.
   - Scopes: add `.../auth/drive.file`.
   - **Test users**: add all 5 of your Gmail addresses here. This keeps the app
     in "Testing" mode (no Google review needed) and works for up to 100 users.
4. **APIs & Services → Credentials → Create credentials → OAuth client ID**:
   - Type: **Web application**.
   - Authorized redirect URIs: add both
     `http://localhost:8000/oauth/callback` (local testing) and
     `https://<your-app-name>.onrender.com/oauth/callback` (prod — use your
     actual Render URL once the service exists).
   - Save the Client ID and Client Secret.

## 2. Local run

```bash
cd multidrive
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# fill in GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, SECRET_KEY in .env
export $(cat .env | xargs)   # or use python-dotenv / your own loader
uvicorn app.main:app --reload
```

Open http://localhost:8000, click **+ add google account** five times (one
per Gmail), pick a distinct label each time (`acc1`...`acc5`), grant access.
Each add is a separate OAuth consent — Google will let you pick which of your
logged-in Google accounts to authorize per attempt.

## 3. Deploy to Render

1. Push this folder to a GitHub repo.
2. Render dashboard → **New → Blueprint** → point at the repo (`render.yaml`
   is already set up: web service + free Postgres for metadata).
3. Set `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `REDIRECT_URI` in the
   service's environment tab (`REDIRECT_URI` = `https://<app>.onrender.com/oauth/callback`).
   `SECRET_KEY` and `DATABASE_URL` are auto-generated by the blueprint.
4. Go back to Google Cloud Console and add the real Render redirect URI to
   the OAuth client if you haven't already (step 1.4).
5. Deploy. Visit the URL, connect your 5 accounts, done.

**Why Postgres and not SQLite in prod:** Render's free web service disk is
wiped on every deploy/restart. The blueprint provisions a free Postgres DB
for the file/chunk index instead, which is what actually matters — your
data itself lives in Drive, this DB only stores the map of "which chunk is
in which account."

## How it works

- Each connected account gets its own `MultiDriveStore` folder in that Drive.
- On upload, the file is split into chunks (`CHUNK_SIZE_BYTES`, default 3GB).
  Each chunk goes to whichever connected account currently has the most free
  space (checked live via Drive's `about.get` quota, minus a safety margin).
- A Postgres/SQLite row tracks `file → ordered chunk list → (account, drive
  file id)`. Download streams chunks back in order and concatenates them.
- Delete removes every chunk from every account, then the index row.
- Nothing is stored unencrypted except the file bytes themselves (which just
  live in your own Drives, same as if you'd uploaded manually). OAuth refresh
  tokens are Fernet-encrypted at rest using `SECRET_KEY`.

## Known limits

- The 15GB free tier is shared with Gmail/Photos on that account, so actual
  usable free space per account may be less than 15GB if you use those.
- No resumable/partial upload recovery yet — if a chunk upload fails
  mid-transfer, the whole file upload fails and no chunks are left orphaned
  in Drive from that attempt's *completed* chunks (you'd need to delete the
  file entry manually via the API if you want to clean those up — there's no
  UI retry yet).
- Files aren't encrypted client-side before upload; anyone with access to
  the underlying Google accounts (or with your `SECRET_KEY` + DB) can read
  the raw file content in each `MultiDriveStore` folder. Add
  client-side AES over the chunks yourself if that matters for your use case.
- Single-writer assumption — it's built for one person's 5 accounts, not
  concurrent multi-user access control.
